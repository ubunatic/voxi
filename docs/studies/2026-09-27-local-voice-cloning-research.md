# Local voice cloning research (2026-09-27)

Three parallel web research reports (luna:med). Decision: prefer tools without a self-managed PyTorch stack.

## Report: zeroshot


Research snapshot: 27 September 2026. Scope: English speech synthesis from a user-supplied reference WAV, with no per-speaker training. “Commercial?” below describes the upstream code/weight terms at the listed versions; it is not legal advice. Hardware speed reports are vendor or project benchmarks, usually on NVIDIA, and do not predict ROCm performance.

## Named models not included in the candidate ranking

- **OpenVoice v2:** useful tone-color conversion / cloning, but the official repository and v2 release did not show qualifying 2025–2026 model activity in the sources checked; therefore excluded under the date constraint.
- **Kokoro:** high-quality compact TTS with preset voices, but not a reference-WAV zero-shot cloning model. “Kokoro-style successor” projects were not treated as candidates unless they accept a reference voice at synthesis time.
- **Sesame CSM:** the released CSM model conditions generation on text plus audio context; it is conversational continuation, not a documented general arbitrary-text voice-clone interface. The released checkpoint is research-oriented and its license is restrictive. Excluded from the core choices.
- **Orpheus:** its released voice set and speaker tokens select trained voices; no supported arbitrary reference-WAV cloning path was found.
- **Dia:** dialogue generation / speaker-conditioned audio, not a supported user-reference voice-cloning TTS interface.
- **Zonos v0.1:** was a viable 2025 voice-cloning model, but superseded here by the actively developed ZONOS2 and its new C++/Vulkan option.

## Recommendation for voxi

1. **Chatterbox Turbo (or Nano when CPU fallback matters):** best initial product candidate. MIT for both code and weights, expressive speech, no transcript workflow, small footprint, and ROCm-capable PyTorch is feasible. Trial on the user’s actual voice because the upstream project does not publish an AMD RTF guarantee.
2. **F5-TTS v1:** strongest low-friction quality probe on this AMD machine because upstream explicitly documents ROCm. The reference transcript is a UX cost and official base checkpoint is non-commercial.
3. **VoxCPM2:** promising balance of expressive naturalness, speaker match, streaming, Apache terms, and a 2B-scale model. Promote it above F5 if the ROCm build works reliably in the target Fedora environment; its high-similarity mode benefits from transcript support.

If AMD GPU compatibility is the primary engineering constraint, add **ZONOS2.cpp** to the first hands-on bakeoff: Vulkan is a more direct non-CUDA route than the Python CUDA-centric projects. If minimizing dependencies is more important than top-tier voice similarity, test **Sopro V2 Turbo** on CPU. Keep all reference and generated voice data local; the model downloads are the only network use required for setup.

## Report: runtime


**Scope.** Linux/Wayland, English voice cloning from user-supplied WAVs, AMD ROCm GPU with about 27 GB VRAM/GTT, and integration behind a Go application. Included projects/models show upstream releases, commits, model updates, or maintained integrations in 2025–2026. “A few seconds” means short prompt conditioning, not personal model training; clarity, low noise, and a transcript where required matter more than accumulating minutes. License statements below distinguish inference code from model weights. This is a deployability assessment, not a listening test on the target workstation.

## Candidates

### 1. Pocket TTS (Kyutai) — CPU-first and unusually integrable

- **Project:** [Pocket TTS](https://github.com/kyutai-labs/pocket-tts); upstream activity throughout 2026. The model is about 100M parameters, English supported, and accepts a local WAV directly as the cloning voice. It documents streaming and ~200 ms to first audio chunk, and roughly 6× real time on an M4 CPU. Those are maintainer measurements, not promises for this AMD CPU. It retains the model in memory in server mode; convert a WAV to a cached voice-state file once to avoid repeated, slower prompt processing. [Upstream README](https://github.com/kyutai-labs/pocket-tts) [Pocket TTS overview](https://kyutai.org/tts/)
- **Audio needed:** Designed for short voice prompts; upstream describes cloning via a WAV but does not specify a strict minimum duration. Community reports commonly use 5 seconds, so treat that as a starting point, not a guarantee. Clean speech is important.
- **Runtime:** Official Python package (PyTorch CPU; no GPU required), CLI, and local HTTP server. It is compact enough that CPU is likely the simplest dependable route on this host; GPU support is experimental, and official guidance says GPU gain depends on CPU/hardware. No need to involve ROCm for the baseline.
- **Native integration:** The upstream README lists community implementations: [PocketTTS.cpp](https://github.com/VolgaGerm/PocketTTS.cpp) is a C++/ONNX Runtime CLI + HTTP server + C FFI; sherpa-onnx supports Pocket TTS with Linux builds and a Go binding; Rust/Candle and Rust/XN alternatives also exist. They are independent ports—check parity, streaming semantics, license, and maintenance before adopting. The Python upstream itself offers `serve`, suitable to prototype a localhost HTTP adapter callable from Go.
- **License:** Upstream code is MIT. Verify the exact selected weight/config and prerecorded voice license separately; upstream points to per-voice license metadata. This is the most promising permissive-licensing option, but do not assume every community checkpoint inherits the same terms.
- **Quality:** Remarkably small for zero-shot cloning, but less expressive/robust than large GPU models is a reasonable expectation; available benchmarks are upstream claims, not direct comparisons. Short inputs can expose prosody and pronunciation limits. Audio streaming is explicit in upstream documentation.

### 2. sherpa-onnx + Pocket TTS or ZipVoice — native deployment toolkit

- **Project:** [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx), active in 2025–2026. It is a C/C++ inference library around ONNX Runtime, ships Linux builds and a C API, has bindings including Go, and provides local/offline TTS APIs. Its supported TTS families now include Pocket, ZipVoice, Piper, Matcha, Kokoro, and others. [Project README](https://github.com/k2-fsa/sherpa-onnx) [C API docs](https://k2-fsa.github.io/sherpa/onnx/c-api/html/index.html)
- **Models/audio:** Pocket TTS is the best fit where an English voice can be supplied as reference audio. ZipVoice has zero-shot cloning and supports English/Chinese; its API requires both `reference_audio` and the spoken `reference_text`. No canonical number of seconds is guaranteed by sherpa docs; use a clean short utterance and evaluate. [ZipVoice docs](https://k2-fsa.github.io/sherpa/onnx/tts/zipvoice.html)
- **Runtime/Go:** Native C++/C API is the key advantage; a Go application can call a Go binding or wrap C ABI, or invoke supplied TTS executables. ONNX Runtime is CPU-ready and supports multiple providers; the exact ROCm/MIGraphX provider availability depends on how the runtime was built and the GPU. Do not assume an arbitrary prebuilt sherpa Linux binary will use ROCm; CPU execution is the low-friction baseline. Batch generation is straightforward. Pocket supports streaming in upstream; ZipVoice reference-conditioned streaming availability depends on API/model version, so confirm the exact interface—many integrations expose cloning as batch/offline synthesis.
- **Latency:** The sherpa docs publish RTF benchmark pages for some configurations, but a single transferable number for this host/model/runtime cannot be stated. Prompt encoding contributes measurable startup work for ZipVoice. Pocket upstream's ~200 ms / ~6× CPU figures are the more relevant published baseline, not a general sherpa guarantee.
- **License:** sherpa-onnx code is Apache-2.0; each model has its own weight terms. The sherpa model registry flags released ZipVoice weights as having no clear license and trained on CC-BY-NC Emilia data; treat these weights as **non-commercial/uncleared** until the actual model card grants rights. Pocket weights/license must likewise be checked at the selected checkpoint. [Model license registry notes](https://docs.rs/sherpa-onnx-models/latest/sherpa_onnx_models/)
- **Quality:** Strong operational fit and portable inference; model choice dictates voice likeness. Pocket's small English model is less heavyweight. ZipVoice is a more TTS-specialized cloning option but licensing and required prompt transcript are drawbacks.

### 3. AMD-PAVS XTTS-v2 ONNX — explicit AMD ROCm packaging

- **Project/model:** [AMD-PAVS-AI/XTTS-v2](https://huggingface.co/AMD-PAVS-AI/XTTS-v2), recently packaged with ONNX Runtime inference and ROCm validation. This is a specifically relevant attempt to bring zero-shot XTTS-v2 to AMD GPU and CPU deployments.
- **Audio needed:** XTTS-v2 is conditioned on a few seconds of reference audio; English is supported. Exact useful duration is content/recording dependent.
- **Runtime:** ONNX Runtime; model card reports ROCm Execution Provider on tested AMD hardware and CPU fallback, with some conditioning work kept on CPU in its documented configuration. It avoids a full PyTorch training stack. Available as model artifacts/scripts rather than a mature Go-native engine; simplest integration is a local Python process or local HTTP wrapper, with Go controlling it over localhost. Check Fedora/ROCm and the card's tested GPU generation before committing: validation on a different AMD architecture does not establish support for this GPU.
- **License:** Weights are marked **Coqui Public Model License (CPML)**, not a permissive commercial license; code and weights must be reviewed separately in the linked repository. CPML restricts commercial use without a separate commercial license. For personal/local use, read the actual terms before bundling or redistribution. [Model card/license](https://huggingface.co/AMD-PAVS-AI/XTTS-v2)
- **Streaming/latency:** Core XTTS generation is not the cleanest low-latency streaming fit; chunked output is possible in wrappers but should not be equated with native incremental low-first-audio streaming. No directly comparable AMD/Fedora first-audio figure found in primary sources.
- **Quality:** XTTS-v2 is a mature, multilingual zero-shot baseline; often strong timbre similarity from a short prompt, with occasional pronunciation/prosody failures. ROCm ONNX work makes this a good hardware experiment, but closed commercial terms and integration uncertainty rank it below Pocket for this case.

### 4. Chatterbox (Resemble AI) — quality-oriented GPU/Python option

- **Project:** [Chatterbox](https://github.com/resemble-ai/chatterbox), released in 2025 and actively developed into 2026. The family includes English and multilingual voice cloning, with current variants up to hundreds of millions of parameters. [Upstream README](https://github.com/resemble-ai/chatterbox)
- **Audio needed:** Upstream advertises cloning from about 5 seconds of reference audio. Supply a clean, representative recording.
- **Runtime/integration:** Python/PyTorch-first package with reference implementation and community local servers. CUDA is the well-trodden path; ROCm compatibility is possible through PyTorch ROCm but not the primary upstream deployment target, so expect dependency/version work on Fedora. No established first-party ONNX/llama.cpp/Rust/C++ inference route identified. For Go, run as a local HTTP service or subprocess and pass WAV/text; do not embed Python into voxi.
- **License:** Code and released weights are presented under MIT by Resemble AI. Check the exact model/version license and third-party dependencies when distributing. [Repository license](https://github.com/resemble-ai/chatterbox)
- **Latency/streaming:** Not a first-audio-latency leader; reference implementation is geared toward generated utterances and chunking rather than low-delay token streaming. No authoritative CPU/ROCm RTF useful for this particular GPU was found.
- **Quality:** Strong naturalness and speaker similarity for the size, plus expressive control; heavier than Pocket and less deployable natively. Attractive if voice likeness is the top goal and ROCm setup is acceptable.

### 5. F5-TTS — capable but Python/weight-license constrained

- **Project:** [F5-TTS](https://github.com/SWivid/F5-TTS) (upstream repository is also surfaced as `cyl67/f5-tts`), with 2025 work including cross-lingual variants. Flow-matching model with chunk inference and a CLI/Gradio server.
- **Audio needed:** Reference WAV **and its transcript** are expected for standard inference; very long prompts are not necessarily better. Few seconds can be tried, but prompt quality/transcript correctness matter.
- **Runtime/integration:** Primarily Python/PyTorch; CUDA inference is the usual documented route. ROCm may run with compatible PyTorch packages but is not a turnkey Fedora ROCm deployment. No mature native ONNX/Go/C++ port was identified. CLI or a local Gradio/API wrapper can be driven from Go.
- **License:** Code is MIT, but the commonly distributed F5-TTS model weights are CC-BY-NC-4.0 (non-commercial). Confirm the exact checkpoint card. [Repository](https://github.com/SWivid/F5-TTS) [weights](https://huggingface.co/SWivid/F5-TTS)
- **Latency/streaming:** Upstream supports chunk inference, but is not inherently a low-first-audio streaming engine; initial inference has multiple flow steps. Paper reports RTF around 0.15 for its setup, which is not an AMD guarantee. [Paper](https://arxiv.org/abs/2410.06885)
- **Quality:** Natural, expressive output and a useful reference-transcript workflow; strong candidate for offline experiments, weaker fit for native integration and commercial distribution.

### 6. CosyVoice 2/3 — streaming-capable but heavyweight deployment

- **Project:** [CosyVoice](https://github.com/QwenAudio/CosyVoice), with Fun-CosyVoice 3 released in late 2025 and ongoing 2026 activity. Supports zero-shot cross-lingual cloning and streaming inference.
- **Audio needed:** A short prompt plus its text/transcript is used for zero-shot voice cloning; the project examples use a prompt/reference text. Not a fine-tuning workflow.
- **Runtime/integration:** Python/PyTorch ecosystem; GPU-oriented, dependencies and deployment stack considerably heavier than ONNX CPU engines. ROCm support is not a turnkey first-party target. Local server/CLI can be wrapped by Go, but there is no broadly established Go/native deployable runtime. Streaming mode is an upstream feature, although actual first audio and stability depend on model/version/hardware.
- **License:** Code is Apache-2.0; verify each checkpoint's model card independently. Public CosyVoice model cards commonly use Apache-2.0, but do not infer this for every 3.0 artifact. [Repository and release notes](https://github.com/QwenAudio/CosyVoice)
- **Latency/quality:** Streaming/KV cache is explicitly optimized; no reliable comparable Fedora/AMD first-audio result located. Potentially excellent naturalness and multilingual speaker similarity, with substantial operational cost for this single-user English feature.

## Deployment takeaways for voxi

- **Prefer CPU-native first:** Pocket TTS's modest model size, CPU-first design, streaming and HTTP/CLI interfaces make it the lowest-risk path. At the Go boundary, a persistent local server avoids model reload; alternatively a C++ port can expose C ABI/HTTP, and sherpa-onnx has Go bindings.
- **Use AMD GPU selectively:** XTTS ONNX from AMD is the clearest targeted ROCm experiment. For Python/PyTorch models (Chatterbox, F5, CosyVoice), ROCm may utilize the GPU but creates packaging friction and does not itself guarantee low latency. The available VRAM is ample for these model scales; compatibility and cold-start/runtime support are the actual risks.
- **Streaming matters:** Pocket explicitly documents streaming and first chunk latency. CosyVoice offers streaming generation. sherpa-onnx makes inference APIs native but model-family feature parity differs. XTTS/F5/Chatterbox wrappers should be treated as request/response or chunked synthesis unless verified end to end.
- **Go integration is straightforward at process boundaries:** Keep the synthesis engine separate from the voxi agent, send text + a locally stored voice ID/reference through localhost HTTP or a subprocess protocol, and return PCM/WAV chunks. For low first-audio latency, keep model and precomputed voice conditioning resident. Native C ABI is possible for PocketTTS.cpp/sherpa but increases upgrade and model-compatibility coupling.
- **Licensing is model-specific:** Apache/MIT runtime code does not grant commercial rights to weights. Pocket's individual voice/checkpoint terms, ZipVoice's unclear weights, XTTS's CPML, and F5's non-commercial weights are material distinctions.

## Ranked top 3 for this case

1. **Pocket TTS, initially via upstream local server; evaluate PocketTTS.cpp or sherpa-onnx binding for production.** Best mix of CPU performance, streaming, HTTP/subprocess fit, and small footprint. Verify the exact checkpoint license and test speaker match with user WAVs. No ROCm dependency.
2. **sherpa-onnx with Pocket TTS.** Best long-term native deployment architecture for Go/Linux: C/C++/C API, ONNX packaging, and language bindings. Prefer Pocket weights; treat ZipVoice as a secondary quality experiment only after resolving weight rights and transcript/prompt handling.
3. **AMD XTTS-v2 ONNX.** Worth benchmarking on the actual AMD GPU because it is explicitly packaged for ROCm and accepts short references; it falls behind due to CPML terms, integration maturity, and weaker evidence for low-latency streaming.

**Alternative when naturalness outweighs a lightweight/native runtime:** Chatterbox is the first experiment; it has permissive licensing claims and short-prompt cloning, but requires a Python/PyTorch service and ROCm validation. F5-TTS and CosyVoice are compelling research candidates, not first choices for a compact Go desktop deployment.

## Report: pipeline


Research date: 2026-09-27. Scope is end-user local TTS/voice-cloning workflows that have repository, release, or model activity during 2025–2026. The advertised minimum clip is a model’s zero-shot conditioning floor, not a guarantee of a stable voice from arbitrary files. Use clean, dry, single-speaker speech with a correct transcript where requested. None of these should upload WAVs during local inference once code and weights are downloaded; avoid hosted demos/APIs for private voice data.

## Recommendation for this machine and product

1. **Qwen3-TTS Base** — first technical spike. It is the best match for current zero-shot cloning quality, short user samples, streaming, and a code+weights license that permits commercial use. The work item is a thin voxi “voice profile” wrapper storing the user’s prompt WAV, transcript, model/version, and consent acknowledgment. Probe PyTorch ROCm support before choosing it as the shipped backend.
2. **Chatterbox Turbo** — best quick local baseline to compare against Qwen. Its prompt-file workflow is simple, weights and code are MIT, output watermarking is a useful provenance measure, and a community has exercised Fedora ROCm. Keep the prompt file as the reusable profile; benchmark actual similarity and latency on the target AMD card.
3. **GPT-SoVITS** — best if the product requirement really means “ingest several recordings and create a persistent adapted voice.” It provides the most integrated prep/fine-tune GUI and claims useful results with one minute. It ranks lower because official GPU setup is NVIDIA-centric and pretrained weight licensing is less straightforward than Qwen/Chatterbox.

F5-TTS and RVC are valuable secondary experiments: F5 for non-commercial prompt-conditioned quality; RVC layered over any stock local TTS when prosody matters and the timbre needs a conversion pass. For RVC, expose it as an optional pipeline rather than presenting it as a TTS engine.

## Product workflow implications

- Offer two paths: **instant clone** (one clean prompt plus transcript; Qwen/Chatterbox) and **adapted voice** (validate/slice a folder, transcribe, let user correct text, train and save a model; GPT-SoVITS). Be candid that seconds enable a first approximation, while a minute or more and varied neutral speech can improve consistency.
- Preserve reusable voice assets locally: prompt WAV + transcript + model ID/version for zero-shot engines; checkpoint + config (and RVC index if used) for trained voices. Provide rename, preview, delete, and export/import. Do not silently copy recordings to a hosted service.
- Add consent safeguards at creation and sharing boundaries: require an attestation that the speaker is the user or has explicitly consented; label generated/exported audio as synthetic where feasible; retain Chatterbox’s watermark; make voice profiles private by default; require explicit action before sharing or publishing. These safeguards reduce misuse but cannot prove consent or prevent downstream impersonation.
- Since the stated input is the user’s own speech, no identity verification is needed for the personal local workflow. If voxi later allows arbitrary third-party voices or sharing, add a stronger consent and provenance policy.

## Source/activity criterion

I excluded older projects that lacked clear 2025–2026 repository/model activity. Qwen3-TTS’s official repo dates release to 2026-01-22. GPT-SoVITS documents its v3 release on 2025-02-28 and later version work. Chatterbox’s repo/model family has 2025–2026 model updates and active installation issues. RVC’s upstream organization lists repository updates in 2026. The date criterion applies to the project/tool workflow, not merely the age of the underlying paper.
